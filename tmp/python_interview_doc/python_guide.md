@@PAGE 04 Python 对象与资源管理
@Q 10 P0 Python 可变默认参数为什么危险
考察点：是否理解函数定义时求值与对象复用。
参考回答：默认参数在函数定义时创建，不是每次调用都重新创建。如果默认值是列表或字典，多次调用会共享同一对象，导致状态串联。安全写法通常把默认值设为 None，在函数内创建新对象。测试要连续调用两次，验证第二次不继承第一次的数据。对 Pydantic 模型或 dataclass 也要使用各自的 default factory。
追问：什么时候故意共享默认对象？答：很少，而且意图不直观。若需要缓存或共享状态，应使用显式的模块对象、缓存装饰器或依赖容器。
@Q 11 P1 生成器和迭代器有什么价值
考察点：能否把语言特性连接到后端场景。
参考回答：迭代器提供逐项读取协议，生成器用 yield 更简洁地保存执行状态。它们适合流式处理大文件、分页拉取和逐块生成响应，避免一次性加载全部数据。但惰性执行也会延后异常和资源释放，所以文件、游标或网络流要有清晰的生命周期，客户端断开时还要停止生产。
追问：生成器一定省内存吗？答：只有消费链路也保持流式时才省。若最后调用 list 或在中间积累全部结果，内存优势会消失。
@Q 12 P1 上下文管理器怎样保证资源释放
考察点：是否理解 with 和异常路径。
参考回答：上下文管理器把获取与释放资源放在 enter 和 exit 协议里，with 块无论正常结束还是抛异常都执行退出逻辑。数据库会话、文件、锁和追踪 span 都适合这种模式。异步资源使用 async with。实际代码还要区分提交、回滚和关闭，不能把 close 当成事务成功。
追问：在 FastAPI 中数据库会话怎么管理？答：常用 yield 依赖或 lifespan 管理，创建后注入请求，finally 中关闭；事务提交与回滚由服务边界明确控制。

@@PAGE 05 Python 数据结构与并发选择
@Q 13 P0 list tuple dict set 怎样选
考察点：基础是否扎实，是否理解复杂度和语义。
参考回答：list 适合有序可变序列；tuple 表达固定记录或可哈希组合；dict 做键值查找并保留插入顺序；set 用于去重和成员测试。平均情况下 dict 和 set 查找接近 O 1，list 中间插入或成员扫描通常是 O n。选择时先看语义，再看访问模式，不能只背复杂度，因为哈希质量、内存占用和数据规模也会影响结果。
追问：为什么数据库结果不直接全放 set？答：set 会丢失重复语义且占额外内存，排序也不保留。应该在 SQL 层完成可下推的过滤和去重。
@Q 14 P1 浅拷贝和深拷贝有什么区别
考察点：能否识别嵌套可变对象的共享。
参考回答：浅拷贝创建外层容器，但内部对象仍共享引用；深拷贝递归复制。配置、请求模板或测试夹具包含嵌套列表和字典时，浅拷贝后修改内部值可能污染原对象。深拷贝并非默认答案，它成本更高，也可能错误复制连接或锁。更好的办法是使用不可变结构、明确构造新对象，或只复制需要修改的层级。
追问：怎样写测试？答：修改副本的嵌套字段，断言原对象不变，并覆盖自定义对象的复制行为。
@Q 15 P0 线程 进程和 asyncio 怎么选
考察点：能否根据负载而不是习惯选并发模型。
参考回答：网络和数据库等待多的 I O 任务适合 asyncio 或线程；CPU 密集任务需要多进程、原生扩展或独立计算服务。CPython 的 GIL 会限制同一进程内多个 Python 线程并行执行纯 Python CPU 代码，但线程仍能覆盖 I O 等待。FastAPI 的异步接口适合异步客户端链路，图片处理或重计算不应直接压在事件循环上。
追问：Celery 属于哪类？答：它是分布式任务队列，可以把耗时或需重试的任务移出请求进程；Worker 内部仍需按任务类型选择进程、线程或其他执行池。

@@PAGE 06 类型系统与 Pydantic
@Q 16 P0 Python 类型注解会在运行时强制校验吗
考察点：是否区分静态分析与运行行为。
参考回答：普通类型注解主要服务于阅读、IDE 和 mypy、Pyright 等静态检查，解释器通常不会自动拒绝错误类型。Pydantic 会在模型创建或显式验证时进行运行时解析与校验。因此边界数据应通过 Schema 校验，内部代码通过类型注解和静态检查减少错误，不能因为写了 str 或 int 就假设外部 JSON 已安全。
追问：Any 有什么风险？答：它会绕过大量静态检查并把错误推迟到运行时。第三方边界可暂时使用，但应尽快收窄到 Protocol、TypedDict 或具体模型。
@Q 17 P1 Protocol 和继承接口有什么区别
考察点：是否理解结构化类型。
参考回答：Protocol 支持结构化子类型，对象只要具有所需方法和属性就满足约束，不必显式继承。这适合为 LLM Client、存储或通知服务定义小接口，便于替换实现和测试。运行时依赖注入仍要提供具体对象；如果需要 isinstance 检查，要谨慎使用 runtime checkable，并知道它只检查结构的一部分。
追问：为什么接口要小？答：小接口降低耦合，测试替身更简单，也减少 Coding Agent 修改无关模块的机会。
@Q 18 P0 Pydantic v2 在 API 中承担什么角色
考察点：是否会把 Schema 当作边界契约。
参考回答：Pydantic 模型定义字段、约束、嵌套结构和序列化形式，可用于请求、响应及工具参数。外部输入默认可能发生类型转换，金额、权限或模型工具参数等敏感边界应考虑严格模式和 extra forbid，避免悄悄接受未知字段。模型验证通过只说明结构符合约束，不能代替业务校验，例如订单归属、余额和状态流转仍需服务层判断。
追问：model construct 能否用于加速？答：它跳过验证，只适合已经可信且经过校验的数据。未经验证的外部输入不能使用。

@@PAGE 07 Asyncio 与 FastAPI 异步边界
@Q 19 P0 async def 为什么不等于自动并发
考察点：是否真正理解事件循环。
参考回答：调用 async def 只会得到协程对象，必须被 await 或创建为 Task 才执行。并发来自任务在等待可挂起的 I O 时把控制权交还事件循环。如果协程内部调用同步 HTTP、同步数据库或长时间 CPU 计算，事件循环仍会被阻塞。排查时要确认依赖库是否原生异步，并通过延迟分布和事件循环阻塞监控验证。
追问：什么时候在 FastAPI 里写普通 def？答：当调用的是阻塞库且暂时不能替换时，可用普通 def 让框架在线程池执行，但还要限制并发，避免线程和连接被耗尽。
@Q 20 P0 怎样给第三方 LLM 调用设置超时和并发上限
考察点：是否能防止外部依赖拖垮服务。
参考回答：我会设置连接、读取和总 deadline，使用 Semaphore 或限流器限制每个 Provider 的并发，并让超时向下游取消传播。重试只针对明确可恢复错误，采用指数退避和随机抖动，同时受总 deadline 与次数限制。请求还要有幂等标识和 trace id。若服务已经过载，应快速返回可解释错误或进入队列，而不是无限等待。
追问：取消任务后 finally 会执行吗？答：通常会在取消异常传播时执行，所以清理应放在 finally。不要吞掉 CancelledError，否则结构化并发和超时可能失效。
@Q 21 P1 asyncio gather 和 TaskGroup 怎样选
考察点：是否理解并发任务的失败语义。
参考回答：gather 适合收集一组已知 awaitable 的结果，但要明确某个失败时其他任务是否继续。TaskGroup 提供更清晰的结构化并发边界，一个任务发生未处理异常时会取消其余任务并在退出时汇总异常。无论选择哪种，都要限制任务数量、处理取消并保证资源释放。批量调用模型时还要避免一次创建成千上万个 Task。

@@PAGE 09 HTTP 与 REST API
@Q 25 P0 POST 请求怎样实现幂等
考察点：是否会处理网络重试造成的重复副作用。
参考回答：客户端为一次业务操作生成 Idempotency Key，服务端把它与用户、接口和规范化请求摘要绑定。第一次请求创建处理中记录并执行；相同 key 和相同参数返回原结果，不同参数则拒绝。数据库唯一约束用于处理并发竞争，外部调用也要传递稳定业务单号。只在内存里查 key 无法跨进程或重启保证幂等。
追问：请求超时但服务端成功怎么办？答：客户端用同一 key 查询或重试，服务端返回已完成结果。不能新建业务单号再次执行。
@Q 26 P0 怎样设计统一错误响应
考察点：API 是否可调试又不泄露内部信息。
参考回答：响应应包含稳定错误码、面向调用方的说明、请求或 trace id，以及必要的字段级校验信息。HTTP 状态码表达协议层类别，业务码表达具体原因。内部堆栈、SQL 和密钥不能返回给客户端，但应与 trace id 关联写入日志。第三方错误要做归一化，并区分可重试、不可重试和需要人工处理。
追问：所有业务错误都返回 200 可以吗？答：会削弱网关、监控和客户端的标准行为。应合理使用 4xx 与 5xx，并在响应体补充业务码。
@Q 27 P1 API 分页 版本和鉴权怎样设计
考察点：能否兼顾演进与数据隔离。
参考回答：数据变化频繁时优先游标分页，并用稳定、唯一的组合排序键；小型后台可使用 offset，但要说明一致性和性能边界。破坏性变更通过版本或兼容字段演进，删除字段要有迁移窗口。鉴权负责确认身份，授权要在资源访问处校验归属和角色，不能只验证 JWT 合法就允许读取任意 ID。
追问：前端隐藏按钮算授权吗？答：不算。后端必须在每个敏感操作处做权限与资源归属检查。

@@PAGE 10 PostgreSQL 与 SQLAlchemy
@Q 28 P0 一条查询变慢怎样定位
考察点：是否能从证据而不是猜测开始。
参考回答：先用 trace 或慢查询日志确认具体 SQL、参数范围和耗时分布，再看 EXPLAIN ANALYZE、实际行数、扫描方式、排序和回表情况。检查筛选、连接、排序是否有匹配索引，统计信息是否准确，是否出现 N 加 1 或一次读取过多列。索引会增加写入和存储成本，因此必须围绕真实访问模式建立，并在接近生产的数据量上验证。
追问：复合索引顺序怎么定？答：根据等值过滤、范围条件、排序和选择性综合决定，并用执行计划验证，不能只背最左前缀。
@Q 29 P0 事务隔离和行锁怎样回答
考察点：能否解释并发行为。
参考回答：PostgreSQL 默认 Read Committed，每条语句看到语句开始前已提交的数据。一个事务内两次查询可能得到不同结果。需要原子推进状态时，我会使用带旧状态条件的 UPDATE 并检查影响行数，或在确需读取后修改时使用 SELECT FOR UPDATE。更高隔离级别能减少异常，但也可能增加冲突和重试，不能替代业务幂等。
追问：死锁怎样处理？答：统一锁顺序、缩短事务、避免事务内远程调用，并捕获数据库死锁错误后对可重试操作做有限重试。
@Q 30 P1 SQLAlchemy Session 和连接池有哪些坑
考察点：是否理解 ORM 背后的资源。
参考回答：Session 是工作单元和身份映射边界，不应作为跨请求全局对象。请求结束必须提交或回滚并关闭。连接池大小要和 Worker 并发、数据库上限一起计算，多进程部署后总连接数会相乘。N 加 1、懒加载越过会话生命周期、长事务以及连接未释放都会造成问题。排查要同时看应用池等待、数据库活动连接和慢 SQL。
追问：池开得越大越好吗？答：不是。过大可能让数据库上下文切换和锁竞争更严重，应根据容量和压测结果设置。

@@PAGE 11 Redis 一致性与并发控制
@Q 31 P0 你在项目里怎样使用 Redis
考察点：能否讲清数据性质与失效策略。
参考回答：简历中的场景包括 Celery Broker 或结果协作、会话和任务上下文、缓存以及验证码类短期数据。每种用途需要不同的 key 设计、TTL、序列化和故障策略。会话状态要考虑过期后如何恢复，缓存可以丢但要防止穿透和击穿，队列则要关注可靠投递和积压。面试时我会选一个自己真正实现过的链路展开，不把 Redis 的所有数据结构都说成用过。

@Q 32 P0 Cache Aside 怎样保持一致
考察点：是否理解缓存只是副本。
参考回答：读时先查缓存，未命中读数据库并回填；写时先提交数据库，再删除缓存。删除失败要有重试或消息补偿，并设置合理 TTL。并发下仍可能读到旧值，强一致决策应直接读权威库或带版本号。热点 key 要防击穿，空结果可短暂缓存，但要避免恶意 key 造成穿透。

@Q 33 P1 Redis 分布式锁怎样实现才安全
考察点：是否会识别锁过期与误删。
参考回答：获取锁使用带过期时间的原子 set nx，value 写唯一 token；释放时用 Lua 比较 token 后删除，避免删掉别人的锁。任务执行时间可能超过租期，需要评估续期或改用数据库状态机。即使锁实现正确，进程暂停或网络分区仍可能让两个执行者先后进入，所以关键写入还需要唯一约束、版本号或 fencing token 兜底。
追问：有锁就不用幂等了吗？答：不用。锁控制并发窗口，幂等保证重复请求或重试不会产生重复副作用，两者解决的问题不同。

@@PAGE 12 Celery 与异步任务
@Q 34 P0 Celery 为什么会重复执行任务
考察点：是否理解消息确认和故障恢复。
参考回答：Worker 在执行中崩溃、确认丢失、可见性超时或调用方重试，都可能让同一消息再次被处理。工程上通常按至少一次语义设计，而不是假设恰好一次。任务要有稳定业务 key，写入用唯一约束或条件更新，外部副作用记录执行状态。确认时机、超时和重试参数要与任务耗时匹配。

@Q 35 P0 Celery 重试怎样设计
考察点：能否区分瞬时与永久错误。
参考回答：网络超时、限流和部分 5xx 可以在总时限内指数退避并加入抖动；参数错误、权限错误和数据缺失通常不应盲目重试。每次失败记录分类、attempt 和下次时间，超过阈值进入失败队列或人工处理。重试不能重新生成业务标识，也不能在未知结果时重复调用非幂等第三方接口。
追问：第三方超时怎么办？答：先按业务单号查询结果；若对方支持幂等 key，用同一 key 重试；否则进入不确定状态并人工核对。
@Q 36 P1 长任务如何展示进度和支持取消
考察点：任务状态模型是否完整。
参考回答：创建任务时返回 task id，服务端持久化 queued、running、succeeded、failed、cancelling 和 cancelled 等状态，并记录版本与时间。Worker 分阶段更新可解释进度，客户端轮询或订阅事件。取消不是只改前端状态，Worker 要在安全检查点读取取消标志并停止后续副作用。结果和日志应有保留期限，状态更新用条件写避免旧 Worker 覆盖新状态。
追问：Celery revoke 能保证立刻停止吗？答：不能把它当成业务级强保证。已运行任务能否终止取决于执行池和信号处理，关键流程仍需协作式取消与状态校验。

@H Python 题 带并发上限的调用
题目：并发调用一组异步接口，最多同时五个，单项超时后记录失败，并保证许可释放。
@CODE async def call_one(item, client, limiter):
@CODE     async with limiter:
@CODE         try:
@CODE             async with asyncio.timeout(3):
@CODE                 return await client.fetch(item)
@CODE         except TimeoutError:
@CODE             return {"item": item, "status": "timeout"}
答案：Semaphore 形成并发上限，async with 保证退出时释放许可，timeout 控制单项时间。生产代码还要处理取消、错误分类、trace id 与总 deadline，不能无限创建 Task。
@H SQL 题 游标分页
题目：查询某租户已完成任务，按 created_at 和 id 倒序，每页二十条。
@CODE SELECT id, created_at, status
@CODE FROM task
@CODE WHERE tenant_id = :tenant_id AND status = 'SUCCEEDED'
@CODE   AND (created_at, id) < (:last_time, :last_id)
@CODE ORDER BY created_at DESC, id DESC
@CODE LIMIT 20;
答案：第一页省略游标条件；联合索引可围绕 tenant_id、status、created_at、id 设计并用执行计划验证。id 打破相同时间的排序并列。游标分页减少大 offset 扫描，但不是跨时刻一致快照。
@H 代码题 LRU 与 TopK
LRU 可用 dict 加双向链表实现，访问或更新后移动到头部，超容量淘汰尾部，平均 O 1；说明结构默认非线程安全。TopK 可维护大小为 K 的最小堆，时间 O n log K，空间 O K。现场写完要主动覆盖 K 小于等于零、K 大于数据量、重复值和空输入。
@H SQL 题 条件更新实现状态推进
@CODE UPDATE task SET status = 'RUNNING', version = version + 1
@CODE WHERE id = :id AND status = 'QUEUED' AND version = :version;
答案：只有影响一行才获得推进资格。外部调用放在可控事务边界之外，并以稳定业务 key 做幂等；不能持有数据库事务等待长时间模型调用。

@@PAGE 26 系统设计 AI 代码问题处理服务
@H 设计题
设计一个服务：用户提交 GitHub Issue，系统读取指定仓库上下文，由 Coding Agent 给出补丁，在隔离环境运行测试，人工确认后合并。
@H 回答框架
入口服务验证用户与仓库权限，创建不可变任务和幂等 key。任务表记录 QUEUED、ANALYZING、PATCHED、TESTING、WAITING_REVIEW、APPROVED、FAILED 和 CANCELLED，并使用版本号做条件更新。API 只负责创建与查询，长任务进入队列。
Worker 在隔离工作区检出固定提交，给 Agent 最小文件与仓库规则。Agent 只能在授权路径编辑，不能访问生产凭据。补丁生成后运行 Ruff、类型检查、单元测试、集成测试和依赖安全检查。测试日志、diff、模型版本、Prompt 摘要和 Token 成本作为产物持久化。
人工审查页面展示需求、基线提交、补丁、测试和风险。只有具备权限的用户可以批准。批准后再次确认分支未漂移；若基线变化则重新应用和测试。合并操作使用幂等 key，失败进入可恢复状态，不让模型直接操作主分支。
@H 面试官可能追问
怎样防止恶意仓库指令影响 Agent？把仓库内容作为不可信输入，工具权限与系统规则由外层执行器控制。
如何隔离代码执行？使用短生命周期容器、无默认网络、只读基础镜像、CPU 内存时间限制和临时凭据。
怎样评测系统？统计补丁通过测试率、人工采纳率、回滚率、首次结果延迟、总成本和不同缺陷类型的成功率。
怎样恢复？任务每一步写 checkpoint，副作用幂等；Worker 重启后从已确认状态继续，未知外部结果先查询再重试。
